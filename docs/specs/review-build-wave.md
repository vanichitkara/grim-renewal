# Review: build-wave-2026-11-22

Owner's ask, restated: share "what worked to cancel company X" across users (the headline feature), build the rest of the suggested items, and replace the walking reaper with doors and windows that the reaper visits and knocks out, so it scales past 5 or 6 subscriptions.

Reviewer only. No source changed. Not checked: nothing was run (no tests, no browser, no deploy). Findings come from reading the plan, `src/types.ts`, `src/pipeline/gmail-scout.ts`, `src/server/bridge-core.ts`, `src/animation/hallway.ts`, `src/ui/app.html`, `package.json`, `vite.config.ts`, `.github/workflows/pages.yml`, `.gitignore`. Sprite pixel sizes and the Google OAuth policy text were not read.

## BLOCKERS

1. **The shared tips cannot work on the live site as planned.** The site is https on GitHub Pages. The API binds `127.0.0.1:8788` over http. Browsers block https to http (mixed content), except to localhost in some browsers. Nothing says where the API runs, who sets `window.GRIM_COMMUNITY_URL`, or how the build gets it. `app.html` (owned by D) holds the inline `GRIM_CLIENT_ID` script; `vite.config.ts` and `pages.yml` have no owner. Cloud Run needs a Google account and billing: that is an ask-the-owner step. Cold starts (seconds) exceed the 3 s client timeout, so the first visitor always gets the seed. Fix: add an item or owner for deployment. Pick one host with https (Cloud Run, or a Cloudflare Worker), name the owner of `GRIM_COMMUNITY_URL` (a `define` in `vite.config.ts` plus the `pages.yml` env), and raise the timeout to 6 s with one retry. Say plainly in the report that without a deployed https API the feature only works locally.
2. **`node:sqlite` is unsafe here.** `package.json` says `node >=20`. `node:sqlite` needs 22.5 or later, and it sat behind `--experimental-sqlite` until 22.13. CI uses Node 22 (a floating minor), so vitest may fail on `import 'node:sqlite'`. Fix: keep the SQLite store out of the test path (tests use the memory store only), load it by dynamic import, and bump `engines` to `>=22.13`. Or skip SQLite and write a JSON-file store.
3. **Privacy: "anonymous" is overstated.** The payload has no id, but the server sees the IP on every POST, and the plan keeps an in-memory (ip, merchantKey) day counter. That is IP plus "has a subscription to X" held in memory. The plan also says "never log IPs", but Cloud Run logs request IPs by default (platform request logs). A key like `smallclinic.com` or `therapyapp.com` is itself sensitive: a report says this person has that service. Fixes: hash the IP with a daily-rotating salt in the limiter, keep it in memory only, and say that platform logs exist. Add a deny list of sensitive categories, or only accept keys on an allow list (the seed list plus a reviewed list). Store only counts per (key, method) and no per-report time. Use a coarse day bucket only if you need age weighting (see 5).
4. **The privacy exception needs the owner's explicit yes.** `privacy.md` says "Never send subscription data to any third-party endpoint". A first-party server is arguably not third-party, but the merchant key is subscription data. The plan has the worker "tell the owner plainly" inside docs. That is too late and too quiet. Fix: report it as an owner decision before D wires the checkbox. Keep the opt-in text exactly as written, default off, and have `submitOutcome` throw or no-op without `consented: true`. Also check that Google's testing-mode consent and the app's stated policy still match: the consent text on the connect screen says "never share your data". Add a line there, or the claim is false once tips ship. Not verified against Google's policy text.
5. **Interface mismatch: `senderDomain`.** The scout derives `senderDomain` in `parseOne` but the `ReceiptFields` shape, the `Accumulator` and `Subscription` do not carry it. B must add it to `ReceiptFields` (owned by nobody: it lives in `src/types.ts`, B owns "additions only", fine) and to the accumulator and the grouping. `parseReceipt(text, domain, date)` already receives the domain, so `parse-receipt.ts` must return it. The plan lists those files for B but never states this chain. `chargeDates` has the same gap: the scout keeps only `chargeCount`, `latestDate`, `totalSpent`, so dates must be pushed in the accumulator loop. Fix: spell out both chains in B's step 1.
6. **Item D "starts after A and B land" but needs C's API too.** D wires `setPage`, `getPageInfo`, `celebrateVerified` (step 7). C should land before D's step 7, or D must code against a stub. Fix: the order is A, B, C, then D; or D starts with stubs for C. Also `demo-data.ts` is D's, but B's new required field `chargeDates` breaks every `Subscription` literal in `demo-data.ts` and the tests until D runs. B is told to "leave a compatible default": that is not possible for a required field. Fix: make `chargeDates` optional (`chargeDates?: string[]`) in the first commit, or give B ownership of the `demo-data.ts` literals for that one change.

## RISKS

1. **merchantKey collisions and the suffix list.** `help.netflix.com` to `netflix.com` works only with a public-suffix list. A small hand list fails on `.com.au`, `.co.in`, `.com.br`, and on shared hosts (`shopify.com`, `substack.com`, `github.io`, `amazonaws.com`). Billing providers send many receipts (`paypal.com`, `stripe.com`, `apple.com`, `paddle.com`): all of those collapse to one key and mix unrelated merchants. Fix: skip keys for known processors (return null, no tips) and add the 2-level suffix list for `co.uk, com.au, co.in, com.br, co.jp, co.nz, com.mx`. Property tests should include these.
2. **Ranking maths.** (a) `minVotes 3 and 60%`: 3 fakes from one actor beat the rule. The limiter allows 20 reports an hour per IP and one per (ip, key) a day, so one IP cannot vote twice a day but a cheap botnet, a VPN, or a day-by-day loop can. Counts are an unauthenticated tally; no design here is poison-proof. (b) Use a Wilson lower bound (95%) instead of a raw rate: 3 of 3 gives about 0.44 and 7 of 9 about 0.45, so a threshold near 0.4 on the lower bound plus a minimum count of 5 (not 3) is a workable pair. Tune with tests. (c) "Half weight after 12 months" needs a report time, which conflicts with the "counts only" store. Keep per-(key, method, month) buckets, or drop decay (the cancel flow changes slowly). (d) "1 fake report must never flip a settled result" is only true if settled means more than the min votes. Test it with numbers, for example 20 true vs 1 false. (e) Methods are not exclusive (a user may have tried email, then phone): ranking by worked-rate per method is fine, but `failed` counts bias toward the method people try first. Say so in docs.
3. **Savings evidence: false "Likely cancelled".** The scout query is `in:inbox (receipt OR renewal OR billing OR "your subscription" OR "trial ending") newer_than:13m`. Cases that look like a cancel but are not: annual plan with the last receipt at 11 to 13 months (the window cuts it, the next renewal is "missing"); a paused or failed payment (receipts stop, still active); a moved or changed sender or subject (query no longer matches); Apple, Google or PayPal billing (receipts come from another sender, merchant parsed wrong); the user's own filter or archive rules (`in:inbox` excludes archived mail, which is a very common receipt setup). The plan lists these in docs but `assessCancellation` has no input for them. Fixes: only assess "likely" when at least 2 charges were seen (so a gap is measurable) and the cadence is monthly or the last charge is under 10 months old for annual; never "likely" for `billingCycle: 'unknown'`; `notes` must name the weak spot; show "Not sure yet" by default for annual plans. Add `in:anywhere` is out of scope (privacy: inbox and promotions only); say that archived receipts are invisible.
4. **"Verified" can be overclaimed.** Verified = Likely plus one full cycle. But "Likely" is itself absence of evidence, so Verified is absence plus time. The label "Verified by email" implies a positive proof. Fix: reserve "Verified" for Confirmed (cancellation email or user claim) plus a cycle with no receipt; call the receipt-gap-only case "No charge seen for a full cycle". Also a user "I cancelled it" claim is the user's word, not evidence of the merchant's: label it "You marked it cancelled".
5. **"Avoided so far" arithmetic.** `monthlyAmount` is already normalised (annual divided by 12), and `projected12m` for an annual plan is one renewal, not 12 x monthly. The plan says "not multiplied by 12 twice" but missed-renewal count times `monthlyAmount` for annual plans is wrong: a missed annual renewal avoids the full annual amount (monthly x 12) once. Define `avoided = missedRenewals x chargeAmount` where `chargeAmount = monthlyAmount x (12 for annual, 1 for monthly)`. Add a test: annual $120, one missed renewal gives $120, not $10 and not $1440. Price changes (kept in the 10-history table) need the last amount, not a mean. Currency is not in `Subscription`: mixed currencies get summed. Say USD-only or add a currency field.
6. **Scene: 8 slots on 480x220.** The current `DOORS` are 4 x-positions at 175, 260, 345, 430 (85 px apart) with a floor at y 184 and a door glow of 80x80. Two floors of four in a 220 px canvas leaves about 90 px per floor; the zombie, the speech bubble (`FLOOR - 52`) and the float text (`FLOOR - 70`) all assume one floor. Windows at about 60 px tall are readable only if the zombie is drawn small or only in the window frame. Risk of unreadable pixel art at 8. Fix: prototype a layout helper first (pure, tested) and view it in Chrome before the knock-out work; fall back to 6 slots (2 x 3) if 8 is cramped. Paging: arrows are fine; also auto-advance the page to the slot being visited, announce it in the aria-live region, and never page while a tween is running.
7. **"Scene advances only on AgentEvents" vs the glide and blink.** A glide or blink to a slot is an approach animation. If it starts at enqueue it is ahead of the backend. Fix: say the approach starts on the `approved` event (already the gate in `reaper.ts`), and the knock-out result animation only on `cancel_ok` or `cancel_fail`; blink and glide must be cancellable (animation.md "every step interruptible"). Also the plan's speed scaling for queues over 8 ("1 knock") changes the visible state machine: keep the `knocking` state, just shorter.
8. **Rewriting `hallway.ts` (1111 lines) with no test file.** `src/animation/` has `graveyard-scene.test.ts` and `sprites.test.ts` but no hallway test. The "existing tests green" bar therefore does not guard the hallway or the graveyard at all. `DOORS`, `FLOOR` and `slots.indexOf(s)` are used at about 15 sites. Fix: C extracts layout and paging into a pure `layout.ts` with tests first, then swaps the call sites; require a Chrome script that runs the 4-sub flow, a trial, the graveyard view and a revenant before and after. Keep the `initHallway`, `addSubscription`, `enqueue`, `onHordeChange`, `setView` signatures stable (D depends on them).
9. **Rate limiting in memory on a serverless host** resets on each cold start and is per-instance, so with more than one instance the limit is not enforced. Document it; Firestore counters or a platform limiter are the real answer.
10. **`isCancellationEmail`** uses a body fetch. The scout fetches the full body only when the snippet fails. Cancellation phrases often sit only in the body, so detection will miss most. Also the Gmail query must match such mails: "has been cancelled" mails often lack receipt, renewal, billing or "your subscription". Fix: add `cancel OR cancelled OR canceled OR "membership ends"` to the query (still a query-level filter, inbox only) and say the detection is best-effort.

- A: tests drive `handle()` only. Nothing proves `client.ts` falls back on timeout, on a non-JSON reply and on CORS failure. Add a fetch-stub test for each, and one end-to-end test: POST three reports, GET shows `best`.
- A: "property tests: idempotent, no @" pass for an empty or wrong key; add a table of real domains (`help.netflix.com`, `mail.spotify.com`, `bbc.co.uk`, `x.com.au`).
- B: "table of 10 histories" is good; also require the exact expected `level`, `avoidedAmount` and `notes` for each, not only "never negative".
- C: "never more than 8 slots drawn" is a unit test of a helper, not of the canvas. The Chrome check "no page errors" does not show that the reaper reached every slot or that results matched events. Require a screenshot of 8 slots and the transition log showing each sub ended `dead` or `boss`.
- D: Chrome check of the header and tabs does not prove `chooseMethod` or the savings numbers are right on realistic data; require a test with the community summary, a receipt link, a phone and none.
- All: no item checks the live Pages deploy. Add a post-deploy `curl` or Chrome check of the Pages URL and of the API `/health` from the Pages origin.
